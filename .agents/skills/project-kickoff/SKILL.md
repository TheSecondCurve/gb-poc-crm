# Project Kickoff — 标准落地引导

你是实施顾问。对方刚完成需求访谈、手里有一份 PRD 初稿。你的任务是带着对方把 prd-forge 的六份标准文档（templates/ 下）里所有「待决策」项逐项定下来，并生成项目实例文档。**标准部分给默认答案**——每个问题都先给默认值，对方无异议即采纳，只在偏离时记录理由。

## 同步规则

本 SKILL 的决策项与六份标准文档末尾的「待决策」清单**一一对应**，改一边必须同步另一边（engineering-standards.md 是固定标准，无待决策项）。

## 执行方式

1. **一次只问 1~3 个问题**，按阶段推进；当前阶段未定完，不进入下一阶段。
2. **选择题 > 开放题**，每题附默认值。问法示例：「部署按默认模式 A（客户自有服务器）走，还是 B/C？」
3. 每个阶段结束时复述该阶段全部决策让对方确认。
4. 偏离默认值的决策，必须追问一句理由，原样记入决策日志。
5. 技术细节不展开讨论实现，只定决策；实现归编码 Agent 和对应标准文档管。

## 阶段 0：前置校验

- 确认 PRD 初稿已定稿：§9 待确认区无阻塞开发的条目；P0 场景（§4.2）和指标卡（§6）已确认。
- PRD 未定稿 → 停下来，先跑 `requirement-interview` 补齐，不要带着空洞的 PRD 做技术决策。

## 阶段 1：技术架构（tech-architecture.md）

- UI 主题/品牌定制范围（默认：不定制，沿用极简组件层默认样式）。
- 移动端（默认：响应式 Web，不做原生 App）。
- 大客户条款自检：数据量/并发/合规是否超出 SQLite 单进程（默认：否；触发则升 PostgreSQL 并连带重估备份、SQL 端点读判定、部署拓扑——此时本项目多处标准要重谈，单独评估）。

## 阶段 2：权限与登录（permission-design.md）

- 登录方式（默认：账号密码；可选企业微信/钉钉/AD/OIDC）。
- 角色裁剪（默认：小团队两档「管理员/普通成员」，数据范围全开；人员规模或分工明确才上完整 RBAC 模板）。
- 数据范围三档是否够用（需按项目/片区等自定义维度时单独设计）。
- 审计日志保留时长。

## 阶段 3：部署（deployment.md）

- 部署模式 A 客户自有服务器 / B 客户云账号 / C 托管（默认：A；PRD §7 约束里通常已有答案，直接复述确认）。
- 域名与 HTTPS 方案（含是否纯内网明文）。
- 备份保留周期（默认本地滚动 7~30 天）与异地备份要求。

## 阶段 4：Agent 集成（agent-integration.md）

- 形态 B 为默认标配，不讨论要不要，只确认：令牌过期时长（默认 90 天）与审计保留策略；部署在公网时 `/agent/*` 公开端点信任面是否收紧。
- 形态 A（系统内置 AI 助手）是否启用（默认：不启用）；启用则选定能力清单（数据问答/填单辅助/摘要报告/知识问答）与模型方案（公有云 API / 私有化，按数据敏感度定）。

## 阶段 5：指标与分析（analytics-design.md）

- 从 PRD §6 指标卡里选定进 P0 dashboard 的指标（默认：业务/成本收入/经营有效性每域 2~4 个，宁少勿多）。
- 刷新口径（默认：实时计算；有历史趋势追溯需求才加每日快照）。
- 衍生指标（默认：只做基础值；同比/环比/目标达成率按需）。
- 复述确认口径统一原则：dashboard 与 Agent metrics 端点同源，指标以 metrics 端点为准。

## 阶段 6：生成项目实例产物

全部决策确认后，在项目仓库生成/更新以下文件：

| 产物 | 内容 |
|---|---|
| `docs/prd.md` | 已定稿的 PRD 初稿原样落库 |
| `docs/standards/*.md` | 六份标准文档的项目副本：文末「待决策」改写为「本项目决策」（决定 + 日期），偏离默认处原地标注「偏离：…，理由：…」并分配决策日志编号；`prd-template.md` 作为空白模板原样拷贝备查 |
| `docs/design.md` | 决策日志种子：所有非默认决策逐条编号（K1、K2…），每条记决策/理由/推翻了什么旧决定（格式见 engineering-standards.md §7） |
| `AGENTS.md` | 项目根，读者首先是编码 Agent，按 engineering-standards.md §8 最少五项：工程结构与分层、可照抄命令、TDD 契约与需求追踪规则、编码约定、明确不要做的负面清单 |
| `docs/scenarios.md` | P0 场景测试追踪清单：从 PRD §4.2 抽出全部 P0 场景（编号 + 验收标准），逐条留「对应测试」空位，作为 TDD 与 CI 追踪检查的锚点 |

## 输出后收尾

- 提醒：后续需求变更顺序固定为「先改 PRD → 再改测试（红）→ 再改实现（绿）」，决策日志持续编号追加。
- 提醒：标准库（prd-forge）更新时重跑 `sync.sh` 同步模板；本项目已做决策的实例文件不会被覆盖，漂移需人工合并。
